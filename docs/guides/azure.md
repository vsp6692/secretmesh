# Azure Key Vault setup

SecretMesh manages Azure Key Vault secrets through its own workload identity (ADR-0012). Connections hold no credentials, and the deployment never stores a client secret for your tenant.

> **Verification status:** the connector is verified against an in-process fake Key Vault and the shared connector contract tests only. It has not been run against a live vault, and `deployments/azure/connector-role.bicep` has not been deployed. Treat the first real connection as a test.

## 1. SecretMesh's own identity

SecretMesh authenticates to your tenant with a federated workload identity, falling back to a managed identity. It never reads client secrets, certificates from the environment, or developer logins (no `EnvironmentCredential`, no Azure CLI).

**Federated workload identity (works across tenants, recommended):**

1. Register one multi-tenant app in the tenant that runs SecretMesh. Add a federated credential for SecretMesh's workload (for example the AKS service account) so that SecretMesh signs in without a secret.
2. Give SecretMesh the usual workload identity environment: `AZURE_CLIENT_ID` (the app's client ID) and `AZURE_FEDERATED_TOKEN_FILE` (the AKS webhook sets both). SecretMesh sets the tenant per connection from `tenant_id`, so `AZURE_TENANT_ID` is not used.
3. In each customer tenant an administrator grants consent to the app. That creates a service principal there; its **object ID** is what you grant access to below.

**Managed identity:** works only when the vault is in the same tenant as SecretMesh's identity. A managed identity cannot obtain tokens for another tenant.

| Setting | Default | Meaning |
|---------|---------|---------|
| `SECRETMESH_ENABLE_AZURE_CONNECTOR` | `false` | Register the Azure provider |
| `SECRETMESH_AZURE_ENDPOINT_URL` | unset | Emulators and tests only. Sends every request to this URL, allows plain HTTP, and must never be set in production |

## 2. Connection settings

A `cloud_admin` creates the connection in SecretMesh with:

| Setting | Meaning |
|---------|---------|
| `vault_url` | `https://<vault name>.vault.azure.net`, also accepted: `.vault.usgovcloudapi.net`, `.vault.azure.cn`, `.vault.microsoftazure.de`. No path, port or credentials |
| `tenant_id` | The Microsoft Entra tenant ID (GUID) that owns the vault |
| `external_id` | Generated by SecretMesh. A value you supply is rejected |

No other settings are accepted. In particular, a client secret, token or endpoint in the config is refused.

## 3. Prove ownership: the marker secret

Azure has no ExternalId, so SecretMesh uses a marker secret instead. Another SecretMesh tenant that learns your vault URL cannot make SecretMesh act on it without this secret.

Create a secret named `secretmesh-external-id` whose value is the connection's `external_id`:

```sh
az keyvault secret set --vault-name <vault> --name secretmesh-external-id --value <external_id>
```

SecretMesh reads it before the first operation and again every 15 minutes, comparing in constant time. If it is missing or different, every call fails with "access denied" and nothing is read or written. A trailing newline is ignored. The marker is not a secret in itself, but keep it: removing it cuts SecretMesh off within 15 minutes.

The names `secretmesh-external-id` and `smstaging-*` are reserved. SecretMesh never discovers them, never reveals them, and refuses them as the name of a secret it creates.

## 4. Permissions (Azure RBAC)

The vault must use the **Azure RBAC** permission model. Deploy the custom role and assignment:

```sh
az deployment group create -g <resource group> -f deployments/azure/connector-role.bicep \
  -p vaultName=<vault> secretMeshPrincipalId=<object id of SecretMesh's service principal>
```

The role grants these data actions on the one vault and nothing else (no keys, certificates or vault management):

| Data action | Why |
|-------------|-----|
| `secrets/getSecret/action` | Read the marker, staged values and revealed secrets |
| `secrets/setSecret/action` | Write staged values and promoted versions |
| `secrets/readMetadata/action` | List secrets, tags and versions |
| `secrets/delete` | Soft-delete targets and staging |
| `secrets/purge/action` | Remove staged values permanently (best effort) |

Key Vault RBAC cannot limit access by secret name, so SecretMesh can reach every secret in the vault. Use a dedicated vault, or one vault per environment, for secrets that SecretMesh manages. The template has an optional ABAC condition (`restrictPurgeToStaging`) that allows purging only `smstaging-*` secrets. It is off by default and untested.

SecretMesh purges only its own staging secrets. It soft-deletes targets and never purges them.

## 5. Network

If the vault has a firewall or a private endpoint, allow SecretMesh's egress addresses or run SecretMesh where the private endpoint is reachable. SecretMesh talks only to the configured vault host over HTTPS, refuses redirects, and follows paging links only on that host.

## 6. Placing discovered secrets

Tag secrets in Key Vault, as in AWS:

| Tag | Value |
|-----|-------|
| `secretmesh:environment` | Name of a SecretMesh environment, such as `prod` |
| `secretmesh:classification` | `internal`, `confidential` (default) or `restricted` |

Untagged secrets go to the connection's default environment, and are skipped without one. Key Vault tags belong to a version: when SecretMesh promotes a value it copies the current version's tags and content type onto the new version, so discovery keeps working.

## 7. What you will see in Azure

- **Pending changes (create and update):** a shadow secret `smstaging-<request id>` with the tags `secretmesh-staging`, `secretmesh-request` and `secretmesh-created`. Consumers never read it.
- **Approved changes:** a new version of the target, tagged `secretmesh-op=<journal id>`. That tag is how SecretMesh recognises its own write after a lost response, and why a retry never creates a second version. New secrets also get `secretmesh-managed=true`.
- **Cleanup:** after promotion, rejection or expiry, the shadow secret is deleted and purged. If a crash leaves one behind, the periodic sync removes it an hour after creation, provided no pending, approved or executing request owns it. Only secrets that have the `smstaging-` prefix, a request ID as their name and the `secretmesh-staging` tag are removed this way.
- **Deletes:** a soft delete. The secret stays recoverable for the vault's retention period.

## 8. Limits and caveats

- **Value size and type:** Key Vault stores text up to 25 KiB. SecretMesh rejects larger or non-UTF-8 values when they are submitted.
- **Purge protection:** with purge protection on, a staged value cannot be purged. It stays soft-deleted in your vault until retention ends. It exists nowhere else, but it is not gone immediately.
- **Soft-deleted names:** a soft-deleted secret keeps its name, so creating a secret with that name fails with a conflict until it is recovered or purged by you.
- **Create race:** SecretMesh checks that a name is free and then writes. A different writer that creates the name between the two steps wins, and SecretMesh then fails with a conflict instead of overwriting.
- **Discovery and rotations:** Key Vault's list call returns secret IDs without a version, so SecretMesh cannot see which version is current during discovery. Unlike AWS, changes made outside SecretMesh are not counted as rotations. Rotation is manual-reminder only (no native rotation).
- **Version history:** finding a retried write scans the secret's versions, so very long histories make promotion slower.
- **Not verified live:** see the note at the top.

## Local development

There is no Key Vault emulator in the dev stack. The package tests run a fake vault in process (`go test ./internal/connectors/azure/`), and `SECRETMESH_AZURE_ENDPOINT_URL` can point SecretMesh at another emulator over plain HTTP.
